### Locate the remaining black terrain squares: scorch alpha operand was never bound
- After the base-game asset mount fix restored weapon/impact decals, the dark world-aligned squares around damaged buildings remained. The screenshot evidence (a hard square under a Gatling, a nearby tank with no patch, and terrain pebbles showing through the square) rules out terrain slope/lightmap and the multiplicative RT-baked projection shadow, and points at `W3DScorch`'s crater quads.
- Root cause: `ScorchTextureClass::Apply` sets `D3DTSS_ALPHAOP = SELECTARG1` but never wrote `D3DTSS_ALPHAARG1`. The last terrain pass before `drawScorches()` (`BaseTerrainTextureClass::Apply`, stage 1 "draw texture through the mask") leaves stage 0 at `D3DTA_CURRENT`, whose alpha is the vertex diffuse alpha (1.0). Every crater therefore sampled the correct `EXScorch01` mask but blended with a constant opaque alpha, stamping the full quad as a dark square; the bright holes were terrain/z-fighting through that opaque quad.
- Fix: `TerrainTex.cpp` `ScorchTextureClass::Apply` now binds `ALPHAARG1 = D3DTA_TEXTURE`, matching the contract `W3DProjectedShadow::flushDecals` already uses. Shared `Core/` source, so the Generals base game inherits it.

So the pre-render shadow bake cannot land in its VkImage yet; making it render requires honoring a pre-frame target request and allow-listing `m_dynamicRenderTarget`. ### Batch 11: offline shadow-map capability probe, all four shadow prerequisites measured on both runtimes
- Added a standalone probe `引擎改造/shadow_map_probe.cpp` (not part of the game build) plus `build/shadowprobe/run.bat`, which compiles it with vcvars64/MSVC and runs it four times: System32 `d3d9.dll`, that again under an 8x-MSAA back buffer, a private copy of the game's DXVK `d3d9.dll`/`dxgi.dll` (copied into `build/shadowprobe/dxvkrun/`, the game directory itself untouched), and DXVK again under MSAA. All four produce identical numbers and one failure, and that failure is the finding rather than a regression. Full data in `PS3.0 升级调研/PS3.0升级实施记录.md` section 12.
- Why offline instead of in-match: these are device/runtime capability questions, not look questions. `GetRenderTargetData` readback answers them pixel by pixel with no game window, no save file and no risk to the renderer that currently passes the win64 gate.
- Shadow-map format is decided: **R32F with depth encoded by the shader**. A D24S8 (or D16) depth-stencil texture can be created and written correctly on both runtimes - proven with a `ZFUNC EQUAL` full-frame test quad that passes 1024/1024 texels inside the caster footprint and 0 outside - yet sampling it returns zero contrast in all four channels. `CheckDeviceFormat` reports "sampleable YES" for exactly those formats, so the caps answer cannot be trusted for shadow maps; only a measured readback can. The R32F path round-trips (write 0.375, sample 0.3765) and a 9-tap PCF `ps_3_0` over it matches the CPU reference on 121/121 compared pixels with 128 genuinely partially-shadowed pixels in the penumbra band.
- The 224 pixel-constant budget is now device-level evidence, not a log line: a `float4 Consts[224] : register(c0)` shader reads back c223/c0/c112 correctly, while the *same source* fails to compile against `ps_2_0`. The 32-to-224 wall is a profile limit, so anything emitting ps_3_0 already has it.
- The ledger's inferred 8-stage sampler ceiling is corrected by measurement: all sixteen slots s0..s15 deliver their bound texture inside a `ps_3_0` on both runtimes, despite `MaxSimultaneousTextures = 8`. That caps field governs the fixed-function and vertex-texture stages; the real remaining constraint is that the deferred `Set_Texture` dirty-mask still stops at stage 7, so s8+ needs direct binding or a rebind each frame.
- `vs_3_0` over the terrain FVF (`D3DFVF_XYZ|DIFFUSE|TEX2`, measured offsets pos@0, diffuse@12, uv0@16, uv1@24, stride 32) works through the FVF-derived declaration the CompatLib shim produces, which makes M2.0 route A viable. Two numbers came out of it: coverage is exactly x[8,23] y[8,23] (256 pixels for a 16x16 patch), proving the `w = 1` padding and the FVF position register; and a least-squares fit of the attribute plane crosses at x 7.912/24.104 and y 8.003/24.008 where the geometry intends 8.0/24.0, so the interpolant is evaluated at the **texel corner** and any `world / texsize` shadow uv must carry a +0.5 texel bias or every receiver comparison lands half a texel off.
- Depth bias calibrated: `D3DRS_DEPTHBIAS = -0.002` moved stored depth from 0.3000 to 0.2980 exactly, and a slope-scale of 2.0 contributed nothing on a fronto-parallel quad - which is why constant bias is a precise [0,1]-range offset and peter-panning/acne fixes need the slope term.
- Two runtime behaviours every future off-screen pass must respect. First, **native Direct3D9 silently discards primitives when the bound depth-stencil surface is not the same size as the colour render target** (no error code; DXVK tolerates it) - the first native run drew nothing at all and looked like a broken harness until the pairs were matched per size. Second, off-screen render targets are not zeroed at creation, so a coverage or pixel-count assertion measures the previous case unless the scene is cleared to transparent black inside `BeginScene`.
- Compile-side facts worth keeping: Direct3D9 has no three-argument `SetRenderTarget` (colour and depth bind separately, which is what `DX8Wrapper` hides), `D3DRS_ZFUNC` takes `D3DCMP_*`, `D3DCAPS9` has neither `MaxPixelShaderConst` nor `MaxPixelShaderValue` so the PS constant count can only be measured, and `PixelShaderVersion` carries the major version in the high byte (0x0300 = 3.0; nibble maths prints 0.0). Inline HLSL under `D3DCOMPILE_ENABLE_STRICTNESS` rejects `sampler2D` with X3086 while the engine assembles its shader bodies through `D3DXAssembleShader` in `GeneralsMD/Code/CompatLib/Source/d3dx9_compat.cpp` - two front ends with different acceptance rules.
- Instruction-slot divergence between stacks: ps_3_0/vs_3_0 slots report 4096 on native and 32768 on DXVK, so long shaders are designed against 4096.
- Documents updated from measurement: ledger section 12 added with sections 7.6/7.7 corrected in place, `PS3.0 阴影升级/工作进度.md` gained the session-2 findings, and `软阴影修改流程.md` M0/M1/M2.0 rewritten (R32F format, removed the non-existent caps field, bias units, HeightMap.cpp actually lives in `Core/GameEngineDevice/Source/W3DDevice/GameClient/`). - Four harness bugs masqueraded as shader bugs, all worth remembering:
  - `A8R8G8B8` names a **bit layout**, so in little-endian memory byte0 is B; splicing bytes as R,G,B produced an exact channel inversion in every mismatch. Fix: `memcpy` the whole word.
  - Native d3d9 rejects `DrawPrimitiveUP` outside a scene (`D3DERR_INVALIDCALL`) while DXVK tolerates it, so a DXVK-only test hides a compliance bug. Fix: bind the RT, then `BeginScene`/`EndScene` around every draw, and print the HRESULT on failure.
  - `D3DPOOL_DEFAULT` `LockRect` returns `INVALIDCALL` with a null `pBits` (crash); `MANAGED` locks fine.

Bisected with harness-authored inline probe shaders (constant write / per-channel scale / COLOR0 passthrough, quantised vs continuous). Fix: a **planar** attribute whose four corner values are exact multiples of 1/255, plus a `VertexColorGPU` reference that quantises at the corners. Any future pixel-differential work must obey this constraint.

Residual risk recorded: `DX8Wrapper::_Reset` does not clear the `Vertex_Shader` cache.
