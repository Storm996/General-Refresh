## 2026-10-25 - Menu/UI architecture investigation: decoupling the shell from WND and C++

- **Question**: the main menu and the ESC pause menu are expensive to change; adding one setting
  needs a C++ rebuild plus a WND gadget. Is the menu UI bound to the in-game UI/gameplay, and can
  it be rebuilt in a simpler way?
- **Findings**: menus are plain `WindowLayout`s over one global `GameWindowManager`, drawn in the
  same 2D batch as the HUD (`W3DInGameUI.cpp:506`) but with no gameplay/CRC dependency. The shell
  stack survives a whole match (`Shell::hideShell` only hides), and the main menu floats over a
  real map running in `GAME_SHELL` unless `ShellMapOn = no`. The ESC menu is not on the shell
  stack at all (created on demand in `QuitMenu.cpp`), so it is the cheapest screen to replace.
- **Root cause**: one screen is authored in three places - `.wnd` geometry and three draw states
  per control, C++ identities/labels/behaviour/settings metadata, and `FunctionLexicon` +
  transition INI names.
  No layout primitives exist, and the 800x600 4:3 layouts are stretched 2.4x/1.8x at 1080p
  (`GameWindowManagerScript.cpp:527`), which also explains the "ugly" look.
- **Cost measured**: `MainMenu.wnd` 205 KB / 62 windows, `OptionsMenu.wnd` 419 KB / 89 windows,
  `GraphicsOptions.wnd` 337 KB / 50 windows; one option row = 50 (bool) / 126 (slider) / 291
  (combo) WND lines plus a 49-line label. Deploy copies only `RightSidebar.wnd`, so WNDs are
  copied by hand. Options already have a `GameOptionDesc` registry (`OptionsMenu.cpp:861`) and
  three generic loops - the right seed for a data-driven page.
- **Recommendation**: keep `GameWindowManager` as the runtime and replace the authoring layer.
  Phase A: settings descriptors + hook table + auto-generated settings page (data-only for normal
  options, no WND, no label in C++). Phase B: `*.menu` document loader + layout/style/action
  layer, then replace the pause menu and main menu with data screens. No ImGui/CEF: it would
  duplicate input/IME/font handling for no functional gain.
- **Doc**: `docs/WORKDIR/support/MENU_UI_ARCHITECTURE_ANALYSIS.md` (architecture, measured costs,
  draft data format, phases, guardrails). No code changed in this session.

## 2026-10-24 — Bush/tree card flicker and stretched triangles (Vulkan)

## 2026-10-28 - Object lighting root cause: double sRGB decode; global sun x1.5

- **Root cause found for "buildings/vehicles are still dark"**: the rig decodes every light colour exactly
  once and T1.6 publishes that finished snapshot into `m_myLight[0..1]` / `Set_Ambient_Light`;
  `DX8NormalMap::Apply` decoded the same values a second time, so objects shaded with `sun^2.2` while the
  terrain (which reads `fpEnv` directly) kept the right value. Measured with the new `GENERALSX_GN_DUMP`
  probe: `lightRaw=(0.364,0.307,0.243)` reached the shader as `c9=(0.109,0.077,0.048)`, ambient
  `(0.181,0.236,0.323)` as `c4=(0.027,0.045,0.085)`. That is why the earlier 1.8 (GN) and 1.6 (FF)
  compensation gains produced no visible change: they multiplied an already-crushed base.
- **Fix**: object and fixed-function paths no longer decode engine light colours (lenv ambient/keys,
  `D3DRS_AMBIENT`, directional slots); authored colours (textures, vertex tint, `md/ma/me`, point/spot
